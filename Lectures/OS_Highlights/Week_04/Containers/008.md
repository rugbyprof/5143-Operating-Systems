# 🌐 **Section 8 — Container Networking**

This section answers the key questions:

1. **Does a container automatically have network access?**
2. **Is inter-container communication common?**
3. **How does container networking work?**

---

# 8.1 Do Containers Automatically Have Network Access?

### **Short answer: Yes.**

When a container starts, Docker automatically:

- Creates a **network namespace** for the container
- Connects it to a **virtual Ethernet pair (veth)**
- Attaches that veth to the host’s **docker0 bridge**
- Gives the container:
  - a private IP (e.g., `172.17.0.2`)
  - outbound access to the internet via NAT

This means:

- Containers can **reach external hosts** (e.g., making API calls).
- External hosts **cannot reach the container** unless ports are explicitly published.

**No special configuration is needed in the Dockerfile.**  
Networking is a runtime configuration, not a build-time one.

---

# 8.2 How Containers Reach the Outside World

Default Docker network: **bridge mode**.

The host runs a virtual bridge:

```
[container eth0] ─ veth ─ [docker0 bridge] ─ NAT ─ Internet
```

- Outbound traffic from the container is NAT’d through the host.
- Inbound traffic is blocked unless you use `-p` to publish ports.

Example:

```bash
docker run -p 8080:80 nginx
```

This maps:

- **host port 8080 → container port 80**
- allowing external traffic to reach the container.

---

# 8.3 Do Images Define Networking?

**No.**  
Images do not define networking.

Networking is defined at **runtime**:

- via Docker’s default bridge
- or via custom networks
- or via host networking mode
- or via user-defined overlay networks (Docker Swarm / Kubernetes)

The Dockerfile has **no networking configuration** except environment variables that applications might read.

---

# 8.4 Inter-Container Communication (Yes, Very Common)

Inter-container networking is fundamental for:

- microservices
- parallel tasks
- pipeline-style architectures
- distributed data processing
- multi-service stacks (API + DB, etc.)

Containers on the same Docker network:

- get unique private IPs
- can reach each other by **name** (DNS-based service discovery)
- do not require exposing ports to the host

Example network creation:

```bash
docker network create mynet
```

Start two containers on that network:

```bash
docker run -d --name app1 --network mynet ubuntu sleep infinity
docker run -d --name app2 --network mynet ubuntu sleep infinity
```

Now:

```bash
docker exec app1 ping -c 3 app2
```

Works because of:

- virtual network interfaces per namespace
- internal DNS per network
- traffic routed entirely inside the Linux bridge

# 8.5 Types of Docker Networking

### **1. Bridge Network (default)**

- Containers receive internal IPs.
- Outbound internet works via NAT.
- Inbound requires port publishing.
- Containers on the same bridge can communicate.

### **2. Host Network (optional)**

Container shares the host network namespace:

```bash
docker run --network host ...
```

- No isolation
- Highest performance
- Ports don’t need publishing
- Less secure

### **3. None Network**

Container has _no network_:

```bash
docker run --network none ...
```

- No internet
- No bridge
- Only loopback
- Useful for high-isolation workloads

### **4. User-Defined Networks**

Created via:

```bash
docker network create mynet
```

- Containers can discover each other by name.
- Traffic is isolated from other networks.
- Preferred for multi-container stacks.

### **5. Overlay Networks (advanced)**

Used by orchestration systems:

- Docker Swarm
- Kubernetes (via CNI plugins)

These allow container networking **across hosts**.

# 8.6 Example: API-Calling Container

Assume a Python container that needs to fetch data:

```python
import requests
print(requests.get("https://api.github.com").status_code)
```

You don’t need any special Dockerfile networking config.

Running it:

```bash
docker run --rm my-python-app
```

Works immediately because:

- `eth0` exists inside the container
- The default route points to the docker bridge
- NAT handles outbound traffic

# 8.7 Example: Inter-Container Communication for Parallelism

Run three worker containers and one controller:

```bash
docker network create cluster

docker run -d --name worker1 --network cluster worker-image
docker run -d --name worker2 --network cluster worker-image
docker run -d --name worker3 --network cluster worker-image
docker run -it --name controller --network cluster controller-image
```

Inside the controller:

```bash
ping worker1
curl http://worker2:8000/task
```

This pattern is extremely common in:

- map-reduce style architectures
- distributed simulation
- pipeline execution
- sharded computation
- microservice decomposition
- containerized HPC workloads
- ML training clusters
- CI/CD runners
- databases with replica sets

# 8.8 OS Concepts Illustrated by Networking

Container networking relies on:

### **Network namespaces**

- Isolated routing tables
- Isolated ARP tables
- Isolated interfaces (`eth0`, `lo`)

### **Virtual Ethernet Pairs (veth)**

- Each container gets one end
- Host bridge gets the other

### **Bridges / NAT**

- Kernel-level bridge acts like a virtual switch
- NAT via iptables or nftables provides outbound access

### **Overlay networks (VXLAN)**

- Encapsulate container traffic across multiple hosts
- Still managed by kernel networking stack

---

# 8.9 Quick Summary

- Containers **automatically** get outbound network access.
- Inbound access requires **port publishing**.
- Images do **not** define networking behavior.
- Inter-container communication is **common and fundamental**.
- User-defined networks provide **DNS-based service discovery**.
- Container networking demonstrates:
  - network namespaces
  - veth pairs
  - bridge networking
  - NAT
  - kernel-level virtual switching
