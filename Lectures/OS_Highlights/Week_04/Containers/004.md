# 🧩 Section 4 — Diving into Linux Namespaces

_Linux namespaces are one of the core mechanisms that make containers possible. They provide **per-container views** of global kernel resources._

---

## 4.1 What Is a Namespace?

- A **namespace** provides an isolated instance of a particular global resource.
- Processes inside a namespace see **their own version** of:
  - process IDs
  - hostnames
  - network interfaces
  - mount points
  - IPC objects
  - user IDs, etc.
- Different namespaces can coexist on the same kernel.

**Key idea:**

> Namespaces do not create new kernels. They create new _views_ of the same kernel-managed resources.

---

## 4.2 Types of Namespaces Used by Containers

Common namespace types (especially relevant to Docker):

| Namespace | Flag            | Isolates                             |
| --------- | --------------- | ------------------------------------ |
| PID       | `CLONE_NEWPID`  | Process ID space, process tree       |
| Mount     | `CLONE_NEWNS`   | Filesystem mount points, rootfs      |
| UTS       | `CLONE_NEWUTS`  | Hostname and NIS domain name         |
| Network   | `CLONE_NEWNET`  | Network interfaces, routing tables   |
| IPC       | `CLONE_NEWIPC`  | SysV IPC, POSIX message queues       |
| User      | `CLONE_NEWUSER` | User and group IDs (UID/GID mapping) |

Containers typically use **several namespaces together**, creating the illusion of a separate system.

---

## 4.3 PID Namespace

**Goal:** Isolate the process ID space.

- Inside a PID namespace:
  - Process IDs start at 1 (an "init"-like process).
  - Processes only see other processes in the same namespace.
- The host still sees all processes with **different PIDs**.

### Docker example

Run an interactive container:

```bash
docker run --rm -it ubuntu bash
```

Inside the container:

```bash
ps aux
echo "Container PID:" $$
```

On the host in another terminal:

```bash
ps aux | grep bash
```

**Observation:**

- Inside the container, the shell might be PID `1`.
- On the host, the same process has a normal high PID (e.g., `12345`).

**OS concept illustrated:**

> The same process has different PIDs in different namespaces.

---

## 4.4 UTS Namespace (Hostname Isolation)

**Goal:** Isolate system identifiers like hostname.

- Each UTS namespace has its own:
  - hostname
  - NIS domain name

Inside a container:

```bash
hostname
```

On the host:

```bash
hostname
```

**Observation:**

- The container hostname is usually a short ID (derived from the container ID).
- The host retains its own name.

**OS concept illustrated:**

> Global identity can be virtualized per namespace.

---

## 4.5 Network Namespace

**Goal:** Isolate networking stack per container.

Each network namespace has:

- its own network interfaces
- its own routing table
- its own firewall rules
- its own `/proc/net` view

In a typical Docker setup:

- The host has a **bridge interface** (e.g., `docker0`).
- Each container gets a **veth (virtual Ethernet) interface**.
- The container sees only its own interfaces (e.g., `eth0`, `lo`).
- IP addresses inside the container are different from the host’s.

Inside the container:

```bash
ip addr
ip route
```

On the host:

```bash
ip addr
ip route
```

**OS concept illustrated:**

> Multiple logical network stacks can run on top of a single physical network stack.

---

## 4.6 Mount Namespace (Filesystem View)

**Goal:** Provide independent views of the filesystem hierarchy.

- Each mount namespace has:
  - its own set of mounted filesystems
  - its own root directory (`/`)
- Unmounting or mounting a filesystem inside a namespace **does not affect** other namespaces.

In containers:

- The root filesystem comes from the container image (via OverlayFS or similar).
- Host paths are exposed only if explicitly **bound** (e.g., `-v /host/path:/container/path`).

Inside the container:

```bash
ls /
mount | head
```

On the host:

```bash
ls /
mount | head
```

**Observation:**

- Different sets of directories and mount points are visible.
- Host filesystems are hidden except where explicitly shared.

**OS concept illustrated:**

> Filesystem hierarchy can be virtualized per process group.

---

## 4.7 IPC Namespace

**Goal:** Isolate inter-process communication objects.

- Each IPC namespace has its own:
  - System V IPC objects (message queues, semaphores, shared memory)
  - POSIX message queues

This ensures that IPC used inside a container does not accidentally interact with IPC outside it.

Inside a container, IPC-related tools will show only the namespace-local objects.

**OS concept illustrated:**

> Synchronization and communication constructs can be scoped to a namespace.

---

## 4.8 User Namespace

**Goal:** Map user and group IDs inside the namespace to different IDs on the host.

- Allows **unprivileged** processes on the host to appear as **root (UID 0)** inside the namespace.
- The kernel maps container UID/GID to non-zero, unprivileged host UID/GID values.

This improves security:

- A process that appears to run as root in the container does **not** have root privileges on the host.

**OS concept illustrated:**

> Security and privilege can be virtualized independently of numeric UID/GID values.

---

## 4.9 Combining Namespaces

Containers typically combine several namespaces:

- PID namespace → process isolation
- Network namespace → network isolation
- Mount namespace → filesystem isolation
- UTS namespace → hostname isolation
- IPC namespace → IPC isolation
- User namespace → privilege isolation

Together, they create a **virtual environment** sharing a single kernel but appearing as a separate system.

### Conceptual picture

```text
+----------------------------+
| Linux Kernel               |
|  +----------------------+  |
|  | Namespace Set (A)    |  |
|  |  PID, NET, MNT, ...  |  |
|  +----------------------+  |
|  +----------------------+  |
|  | Namespace Set (B)    |  |
|  |  PID, NET, MNT, ...  |  |
|  +----------------------+  |
+----------------------------+
```

Each “Namespace Set” is what a container runtime presents as one container.

---

## 4.10 Minimal Hands-On Namespace Experiment (Optional, Non-Docker)

For environments where `unshare` is available:

```bash
sudo unshare -p -f --mount-proc bash
```

Inside the new shell:

```bash
echo "Inside PID namespace:"
ps aux
echo "PID here:" $$
```

On the host:

```bash
echo "On host:"
ps aux | grep bash
```

**Observation:**

- Different PIDs for the same shell.
- The `unshare` tool directly exposes the same primitives that container runtimes orchestrate.

---

## 4.11 Summary

- Namespaces are **kernel-level mechanisms** that provide isolated views of global resources.
- Containers are built by combining multiple namespaces:
  - PID, UTS, Network, Mount, IPC, User.
- These mechanisms allow:
  - process isolation
  - filesystem isolation
  - network isolation
  - privilege separation
- Namespaces demonstrate how the OS can present **multiple logical systems** on top of one physical kernel.
